Case study 1 · energy sector, natural gas utility

A notebook-bound R model, rebuilt as an operated ML pipeline.

10× data
processed in about one third of the compute runtime, measured from cloud billing records
~240 features
engineered across about 10 million records
114+ tests
automated, where the legacy code had none
~0.8 AUC
for the non-payment classifier on the rebuilt pipeline

Context

The client’s collections team relied on an XGBoost model that predicts which customers will not pay. Credit losses were rising year over year, so the scores mattered more each month. The model lived in undocumented R notebooks, with no automated tests and no drift monitoring.

Constraints

  • The legacy code came with no documentation and no tests to check a rewrite against.
  • The workflow had to make sense to engineers and to the people operating it.
  • Deployment, validation, and failure behavior were part of the deliverable, not work for later.

What I built

I read the legacy notebooks until I could state what each step did, then rewrote the workflow as a modular, config-driven Python package. Each stage runs as a step in AWS SageMaker Pipelines. The infrastructure is declared in Terraform, and every training run is tracked in MLflow.

Pipeline, by component role

  1. Ingest customer and payment records
  2. Preprocess clean and validate
  3. Features ~240, driven by config
  4. Train XGBoost, tracked runs
  5. Infer non-payment scores
  6. Monitor data and model drift
  • Terraform: infrastructure as code
  • MLflow: experiment tracking
  • Structured logging
  • Resumable runs
  • Automated test suite

What makes it operable

The safeguards added around the model during the rebuild.
Concern Safeguard
Correctness 114+ automated tests over the pipeline code, where none existed
Drift Population stability index, Kolmogorov–Smirnov, and chi-squared checks on data and model outputs
Reproducibility Config-driven runs, each one tracked in MLflow
Failure Explicit error handling, structured logs, and resumable runs
Infrastructure Declared in Terraform, so changes are reviewable as code

Result

The rebuilt pipeline processes ten times the data of the old implementation in about one third of the compute runtime. I took that comparison from the cloud billing records rather than from a benchmark of my own. The collections team now has scores it can use to target its strategies, produced by a pipeline that reports when its inputs change.

What I learned

  • Translating the model code was the small part. The real work was recovering the assumptions the notebooks never wrote down.
  • Reproducibility and handover quality decide whether a model stays in use. Accuracy only gets it considered.
  • My earlier work in retail banking paid off here: knowing how payment delinquency unfolds informed the feature engineering.

Case study 2 · enterprise knowledge engineering

An LLM agent that stopped contradicting itself across departments.

Context

An enterprise LLM agent answered the same question differently depending on which department asked. The main cause was vocabulary: departments used the same business terms with different meanings, and nothing told the agent which meaning applied.

What I built

I worked with the business department to write the shared terminology down as a formal ontology in RDF/OWL, serialized as Turtle (.ttl). The agent receives the ontology directly in its context. I also corrected the model and decoding-temperature configuration, which had been adding variance of its own. 

@prefix ex:   <https://example.org/glossary#> .
@prefix owl:  <http://www.w3.org/2002/07/owl#> .
@prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#> .
@prefix skos: <http://www.w3.org/2004/02/skos/core#> .

ex:ActiveCustomer a owl:Class ;
    rdfs:subClassOf ex:Customer ;
    rdfs:label "Active customer"@en ;
    skos:altLabel "Current account"@en ;
    skos:definition "A customer with an open contract and an invoice issued in the last 90 days."@en .

An illustrative term written for this page, not the client’s vocabulary. One definition, its synonyms, and its place in the hierarchy travel together.

In context, compared with retrieval

The obvious design was retrieval: index the glossary and fetch the relevant pieces per question. I compared the two. Placing the whole ontology in the prompt gave more consistent answers than retrieving fragments of it. A compact vocabulary fits in context whole, so the model sees each term next to the terms it is defined against.

A tool the business could use

The people who own the terminology work on locked-down corporate machines where nothing can be installed. I built a browser-based editor and visualizer for .ttl files that needs no installation, so they could read and change the ontology themselves.

Result

  • The cross-department inconsistency disappeared in the proof of concept.
  • The partnering business department backed adoption, on the strength of the proof of concept and the editor.
  • The terminology now exists as a file people can review and change, rather than as habits spread across teams.

What I learned

  • Test the simple design first. Retrieval was the default, and it was not needed.
  • An agent’s inconsistency is often the organization’s inconsistency. Fixing the vocabulary fixed the agent.
  • A tool that runs where the users are allowed to run it gets adopted.
